# OnCo — Intake / Architecture Review

## Capability

OnCo is a public oncology knowledge-graph project with a Next.js/TypeScript site, static JSON API, OpenAPI output, MCP server, CLI, LLM context exports, schema validation, provenance tooling, fact-checking, freshness checks, scheduled data refreshes and graph backlinks.

Upstream: https://github.com/judegomila/OnCo

## Stack Fit

The strongest value to the reusable builder stack is architectural rather than oncology-specific content:

- schema-first typed domain objects
- graph construction with derived backlinks
- primary-source/date requirements
- duplicate and dangling-reference validation
- static JSON/OpenAPI/RDF/context exports from one canonical corpus
- MCP + CLI over the same data surface
- factcheck / audit / provenance / freshness workflows
- benchmark scripts and scheduled refresh pipelines
- plain-English + technical layered presentation
- explicit gap, bottleneck and completeness tracking

These patterns are reusable for vertical intelligence products such as market intelligence, real-estate research, commerce research, tooling intelligence and other domain-specific agent systems.

## Licensing Boundary

- Software/code: MIT.
- Data corpus: CC BY-NC 4.0 with attribution; commercial data reuse requires separate permission/licensing.
- Logos/trademarks remain owned by their respective owners.

Therefore the project must not be treated as an unrestricted commercial dataset dependency.

## Medical / Trust Boundary

OnCo describes itself as work in progress and requires important facts to be checked against primary sources. It should be treated as a research-navigation and structured-information layer, not as an autonomous diagnosis or treatment authority.

## Benchmark Plan

Compare OnCo against the reusable stack's Agent-Lab / Growth-Research architecture on:

1. schema and relationship model
2. provenance and freshness model
3. API/OpenAPI export design
4. MCP tool surface and safety boundaries
5. graph traversal / backlink derivation
6. corpus validation and failure handling
7. benchmark/evaluation design
8. update automation and source refreshes
9. portability of the architecture without copying restricted oncology data
10. overlap with existing ArchiveBox / Flowsint / Agent-Lab research components

## Decision

**KEEP / BENCHMARK — REFERENCE DOMAIN-INTELLIGENCE ARCHITECTURE**

Do not promote to core. Do not ingest the oncology corpus into commercial products by default. Mirror or reuse code only after confirming that the fork preserves the software/data-license separation and attribution requirements.
